# Documentation and Standards — SPMS

## 1. Introduction

This document establishes the documentation standards and conventions for the Student Placement Management System (SPMS). Consistent documentation is essential for:

- Academic evaluation (demonstrating SDLC knowledge).
- Team communication (even for a single developer, future maintainability requires clear docs).
- Traceability (connecting requirements to implementation to tests).
- Quality assurance (documenting verification and validation evidence).

## 2. Document Hierarchy

## 3. Documentation Standards

### 3.1 General Conventions

| Convention | Standard |
|-----------|----------|
| File format | Markdown (`.md`) for all text documents |
| Heading hierarchy | `#` for document title, `##` for sections, `###` for subsections |
| File naming | Lowercase with hyphens (e.g., `problem-statement.md`) |
| Tables | Markdown tables for structured comparisons |
| Code blocks | Fenced with language identifier (` ```python `, ` ```typescript `) |
| Diagrams | PlantUML source (`.puml`) + rendered exports (SVG preferred) |
| Dates | ISO 8601 format (YYYY-MM-DD) |
| Timestamps | UTC (stored in database and logs) |

### 3.2 Requirement Document Standards

| Convention | Standard |
|-----------|----------|
| Functional requirement IDs | `FR-<MODULE>-<NNN>` (e.g., `FR-AUTH-001`) |
| Non-functional requirement IDs | `NFR-<CATEGORY>-<NNN>` (e.g., `NFR-PERF-001`) |
| Business rule IDs | `BR-<NNN>` (e.g., `BR-001`) |
| User story format | "As a [role], I want [goal], so that [benefit]" |
| Acceptance criteria | Given/When/Then format |
| Priority levels | Must Have, Should Have, Could Have, Won't Have (MoSCoW) |

### 3.3 SRS Document Standard

The SRS follows the **IEEE 830** (now part of ISO/IEC/IEEE 29148) structure:

1. Introduction (purpose, scope, definitions, references).
2. Overall Description (product perspective, functions, user classes).
3. External Interface Requirements.
4. System Features (detailed functional requirements).
5. Non-Functional Requirements.
6. Other Requirements.
7. Appendices.

Every requirement must be:
- **Unambiguous** — only one possible interpretation.
- **Verifiable** — can be confirmed through testing or inspection.
- **Necessary** — traces to a stakeholder need.
- **Consistent** — does not conflict with other requirements.
- **Traceable** — linked to source (stakeholder) and target (implementation + test).
- **Uniquely identified** — has a unique ID.

### 3.4 Design Document Standards

| Document | Standard |
|----------|----------|
| Architecture | C4 model influence (context, containers, components) |
| UML diagrams | UML 2.x notation via PlantUML |
| Database design | Collection schemas, index definitions, relationship diagrams |
| API specification | OpenAPI 3.0+ (auto-generated by FastAPI) |
| Pseudocode | Structured English with clear control flow |
| Flowcharts | Standard flowchart symbols (process, decision, I/O, terminal) |

### 3.5 Test Document Standards

| Document | Standard |
|----------|----------|
| Test strategy | Objectives, scope, approach, entry/exit criteria |
| Test cases | ID, description, preconditions, steps, expected result, actual result |
| Test reports | Summary, pass/fail counts, coverage, defects found |
| Defect reports | ID, severity, priority, description, steps to reproduce, status |

### 3.6 API Documentation Standards

FastAPI automatically generates OpenAPI documentation accessible via:
- **Swagger UI**: `http://localhost:8000/docs`
- **ReDoc**: `http://localhost:8000/redoc`
- **JSON Schema**: `http://localhost:8000/openapi.json`

Conventions:
- Every endpoint has a descriptive summary and description.
- Request and response schemas are defined via Pydantic models.
- Error responses are documented.
- Authentication requirements are specified.
- Example requests and responses are provided where helpful.

### 3.7 Code Documentation Standards

**Python (Backend):**
- Module-level docstrings explaining purpose.
- Function/method docstrings explaining behavior, parameters, and return values.
- Inline comments for non-obvious logic.
- Type hints for all function signatures.

**TypeScript (Frontend):**
- JSDoc comments for exported functions and components.
- Interface/type definitions for all data structures.
- Props documentation for React components.
- Inline comments for complex logic.

## 4. Version Control Conventions

### 4.1 Commit Messages

Follow the **Conventional Commits** specification:

```
<type>(<scope>): <description>

[optional body]
[optional footer]
```

Types:
| Type | Usage |
|------|-------|
| `feat` | New feature |
| `fix` | Bug fix |
| `docs` | Documentation changes |
| `style` | Formatting (no code change) |
| `refactor` | Code restructuring (no feature change) |
| `test` | Adding or updating tests |
| `chore` | Build, CI, or tooling changes |

Examples:
```
feat(auth): implement JWT login endpoint
docs(srs): add placement drive system features
fix(eligibility): correct CGPA comparison for boundary values
test(auth): add unit tests for password hashing
```

### 4.2 Branch Naming

| Branch Type | Pattern | Example |
|-------------|---------|---------|
| Main | `main` | `main` |
| Development | `develop` | `develop` |
| Feature | `feature/<module>-<description>` | `feature/auth-jwt-login` |
| Bugfix | `bugfix/<description>` | `bugfix/eligibility-cgpa-check` |
| Hotfix | `hotfix/<description>` | `hotfix/security-token-expiry` |

### 4.3 Changelog Format

Based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/):

Categories: Added, Changed, Deprecated, Removed, Fixed, Security.

## 5. Review Standards

### 5.1 Code Review Checklist

- [ ] Follows project coding standards (Ruff, ESLint).
- [ ] No hardcoded secrets or credentials.
- [ ] Input validation implemented.
- [ ] Error handling present.
- [ ] Unit tests written for new logic.
- [ ] Documentation updated if needed.
- [ ] No unnecessary dependencies added.
- [ ] API responses follow consistent format.

### 5.2 Documentation Review Checklist

- [ ] Correct heading hierarchy.
- [ ] Tables properly formatted.
- [ ] Requirement IDs are unique and follow convention.
- [ ] Diagrams have source files and rendered versions.
- [ ] No placeholder content left unresolved.
- [ ] Cross-references are valid.
- [ ] Dates use ISO 8601 format.

- [ ] Documentation updated.
- [ ] `CHANGELOG.md` updated.
- [ ] `PROJECT_PROGRESS.md` updated.
- [ ] No critical or high-severity defects open.
- [ ] Docker builds succeed.
- [ ] CI pipeline passes.
